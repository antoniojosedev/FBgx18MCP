# Plan 129 — independent `gx-engine` review

Review date: 2026-10-15. This audits portable engine coverage/security toward the SDK replacement objective. No SDK/native KB, Cloud, or SQL/database was accessed; production code was inspected but not changed by this review, and no Git writes were made.

## Verdict and concrete finding

Full SDK/toolchain replacement is the destination; current `gx-engine` is a standalone compiler for bounded portable inputs, not a drop-in replacement. Portable tests do not prove GeneXus semantics. Existing native observations are narrow/environment-specific; this review ran no native probe.

The initial audit found `src/gx-engine/src/build.rs:203` hard-coding every build manifest's backend as `independent-rust-i64-subset`, including format-2 typed record/collection projects. The regression in `src/gx-engine/tests/sdk_replacement_acceptance.rs` preserves that label for format 1 and expects `independent-rust-typed-subset` for format 2. The owner reported the initial acceptance target failed both this backend expectation and entry canonicalization (`MAIN`, not `Main`); the parent repaired manifest selection, I corrected the expected canonical entry, and my focused target now passes both backend assertions. This review did not edit production code.

## Acceptance coverage

Existing `tests/cli.rs` covers simple format-1 check/run, but not an end-to-end `check -> emit -> build -> run`. Existing `tests/typed_pipeline.rs` covers nested record/collection aliases and clones, and shared step-budget exhaustion for repeated collection/record clones. The new acceptance test uses `fixtures/typed-record-collection.json` to verify check's explicit `SDK parity unverified` status, safe-Rust emit output, equality of emitted source and the published artifact, execution of that artifact, and separate CLI `run`. Expected output observes defaults, record aliases, shallow record-clone aliases, and collection membership/item behavior. It does not claim native parity. The stdout helper now normalizes CRLF only, and its regression input asserts preservation of trailing spaces and blank lines; the E2E expected output includes its final newline.

The format-2 compiler's inlined runtime is distinct from `src/structured.rs` owned deep-copy semantics. The XML projection now admits nested Record/Collection SDT declarations in its bounded portable model; README still marks exact native hierarchy XML build/run differential as pending. Existing portable clone-budget tests are not fresh native evidence.

## Security and resource limits

Reviewed code paths use bounded project/catalog/XML/structured input, validated identifiers/types, rustc argument vectors (not shell), isolated staging, publish-on-success, compiler deadlines and cleanup. Existing tests cover oversized input, invalid schemas/source, compiler failure cleanup, and preservation of prior output. Generated source forbids unsafe code. `run` is explicitly not a sandbox: authored code inherits console I/O, has a 10-second deadline but no memory/disk/output quota, and descendant cleanup is not guaranteed on non-Windows. README correctly says to run only trusted projects. Build generations retain portable input/generated source, which may be private.

## Native evidence and integration gaps

There is no Gateway/Worker dispatch integration or native KB reader/writer in this standalone CLI. Catalog/XML are explicit portable projections, not native KB decoding or lossless interchange. KB/storage, most object families, broader language/runtime semantics, spec/navigation, generator/build orchestration, data access, and MCP integration remain replacement gaps. The acceptance test validates only the portable CLI path.

The README and validation script are appropriately explicit that saved native evidence is narrow and not a fresh general parity run: `scripts/validate_typed.py` consumes an already-verified local native report, checks its source/declarations, and compares one parameterless typed corpus while excluding checked-storage wrap. It does not build or query a native KB itself. The nested record and collection fixtures have portable alias/clone tests, but their exact current integrated native-vs-Rust run is still documented as pending. The clone budget is a Rust resource policy, not a measured native behavior.

## Concrete next acceptance boundaries

1. **Resource amplification (not currently a sandbox contract):** current limits include 1 MiB per `Text`, at most 1,024 fields per record, at most 100,000 collection items, 100,000 shared execution ticks, depth 128, and a 10-second CLI run deadline. `Text` owns a `String`; shallow `Record.Clone()` copies the outer field map and the backend charges field count, while collection Clone copies the item vector and charges item count. Thus a tick is not a byte/memory bound: a record field can contain a 1 MiB Text, repeated clones copy that payload, and Print inherits unbounded console output. README correctly says trusted projects only; do not call this an exposed untrusted-input vulnerability under the current contract. Before untrusted or service-hosted execution, require deterministic memory/output-byte caps and a regression with large Text clone amplification plus output flooding that proves bounded termination/cleanup (avoid tests that intentionally rely on host OOM or timing alone).
2. **Native nested/collection differential:** next native gate should run the exact committed portable nested-record and collection sources (or a hash-identified equivalent) against the same disposable KB/SDK build, capture exact output and exit status, preserve the input KB, and record SDK/build provenance. Check default construction, assignment aliases, nested child aliases after `Record.Clone`, item aliases after `Collection.Clone`, independent membership on add, and failure/rollback. Do not infer this from the existing portable tests or from the prior scalar clone probe.
3. **Exchange-path parity:** the new CLI acceptance covers portable JSON only. For `kb-*`/`xml-*`, add separate acceptance for the same nested/collection semantic fixture through projection, emit, build, and run; verify catalog/XML inputs are unchanged and compare exact output. Current docs correctly call native hierarchy exports available but exact Rust XML build/run differential pending.
4. **Product integration:** before calling this an SDK replacement, an acceptance boundary must exercise a real Gateway/Worker request through dispatch to gx-engine and back, plus the eventual native-KB read/write path. Standalone CLI success is not MCP integration or SDK replacement. Keep session, KB ownership, and authorization boundaries explicit; do not silently add an SDK fallback.
5. **Performance evidence:** current clone tests establish budget failure, not throughput or peak memory. Any performance claim should be backed by a bounded before/after benchmark using representative field counts, text payload sizes, and collection sizes; no such benchmark was run in this review.

## Targeted review of parent For/Str/LEN changes

- `For`: source lowers start once, re-evaluates the limit in the loop condition, chooses `<=`/`>=` from the signed literal step, and charges the shared execution budget per entered iteration. The existing `for_loop` tests cover ascending inclusivity, nesting, bound side effects, and budget exhaustion, but not an explicit negative step. A fresh CLI probe of `For &I = 3 To 1 Step -1` produced `3, 2, 1, 0`; a default positive-step range `3 To 1` did not enter and left the iterator at 3. This is portable execution evidence only, not a new native comparison. A separate focused `cargo test --test for_loop` invocation returned an uncertain tool outcome with no result; it is not counted as passing.
- `Str`: the initial boundary probe found that `Print(Str(79228162514264337593543950335.0,18,18))` failed with `decimal rendering alignment overflow` instead of the width-18 overflow fill. The owner added an early minimum-rendered-width check in `types::format_str` before decimal alignment. The durable acceptance regression now passes, as does the existing `str_format` target (2/2); no remaining issue was observed on this boundary. This is portable evidence, not a fresh native comparison.
- `LEN`: the focused `len_builtin` target passed 2/2, covering trailing ASCII spaces, UTF-16 units (including a supplementary character), empty text, backslashes, and rejection of wrong arity/non-Text operands. No concrete regression was observed; these are portable tests plus previously recorded local native evidence, not a fresh SDK run.
