# Fork Changelog

Changelog for **this fork only** (`antoniojosedev/FBgx18MCP`). It records the
changes the fork owns, so they never produce a merge conflict.

- Upstream (`lennix1337/Genexus18MCP`) never touches this file.
- `CHANGELOG.md` is a faithful mirror of upstream and must stay byte-identical to
  it. Do **not** add fork-local entries there; they go here instead.
- Record each fork-local entry under `## Unreleased`, in the matching
  `### Added` / `### Changed` / `### Fixed` / `### Internal` subsection.

Caveat (fork policy, option A): the upstream-owned
`scripts/integration-preflight.ps1` gate still requires `CHANGELOG.md` to be
touched when a change lands under a "production" path (`src/`, `cli/`,
`scripts/`, `install.ps1`). That gate runs for pull requests; this fork pushes
directly to `main`, so it does not fire in the normal flow. If a fork PR is ever
opened, expect the gate to ask for a `CHANGELOG.md` touch — do not resolve it by
moving this entry back.

## Unreleased

### Added

- Fork-local Engine backend override helpers: `scripts/Set-GxMcpLocalEngineBackend.ps1` merges only `Engine.Backend` (`sdk|auto|gxengine`) into `publish\config.json`, preserving every other key, writing UTF-8 without BOM and verifying the read-back; `scripts/Invoke-GxMcpLocalBuild.ps1` runs `build.ps1` (or `install.ps1` with `-Install`) as a child process, propagates its exit code unchanged and only then applies the choice. The need exists because `build.ps1` wipes `publish/` (`:112-116`) and regenerates `config.json` from a neutral template (`:207-230`) with no `Engine` section, and a strict document rejects `GXMCP_ENGINE_*` at load, so the file is the only authority; a plain build or install therefore restores the upstream default (`gxengine`). The upstream fix (a `build.ps1` parameter or preserving the section) was reported as https://github.com/lennix1337/Genexus18MCP/issues/649; per fork policy neither upstream script is patched here. Limit: the choice is local and is lost if the upstream entry points are run directly. The `LOCAL POLICY` block in `AGENTS.md` now names the wrapper as the agent default (including the harness-refresh row) and requires the setter after any direct `build.ps1`/`install.ps1`/`release.ps1` run.

- Fork-local pre-push mechanical checker, Rust lanes: each crate gets an advisory lane — `rustLane` for `gx-engine` and `gxwireRustLane` for `gxwire` — running `cargo fmt --check`, `cargo clippy --all-targets --locked -- -D warnings` and `cargo test --locked` in its own directory. `-IncludeRustLane` forces both; without it, a changed range touching `src/gx-engine/` or `src/gxwire/` auto-enables only the matching lane and records `note='auto-enabled-by-changed-paths'` (an explicit force carries no note). All three checks run even after a failure; neither lane feeds `mechanicalFailed`/`mechanicalUnavailable`, enters `summary.phases`, or changes `pushReadiness` (upstream defects are reported, not gated). `-CargoExecutable` is the test seam; missing cargo reports `not-run`/`cargo-not-found`, a missing engine crate `not-run`/`engine-missing`, and a missing gxwire crate `not-run`/`gxwire-missing`. `notCovered` names each lane as opt-in when it did not run and removes it when it runs. Tests use a fake cargo to prove lane separation, ordering, `--locked`, auto-enable by synthetic `changedPaths`, and that a failed lane preserves `readyLocal`.

### Changed

- Fork-local pre-push mechanical checker, default Rust lane selection: a changed range touching `src/gx-engine/` or `src/gxwire/` now runs the matching advisory lane without `-IncludeRustLane`, so a Rust edit is no longer reported as `not-requested`. The answer is still advisory: `pushReadiness` is unchanged, an explicit `-IncludeRustLane` forces both lanes, and `notCovered` no longer claims `gxwire Rust lane` when that lane actually ran. Limit: the decision only looks at `BaseRef..HEAD` (`scripts/Invoke-PrePushMechanicalChecks.ps1:1091`), so an uncommitted Rust edit on its own does not enable the lane (which remains declared as opt-in in `notCovered`), although cargo covers the working tree when the lane was already enabled by the range or by `-IncludeRustLane`; the lane can stay red while #641, #643 and #659 remain open.

- Fork-local pre-push mechanical checker: whitespace-hygiene findings (`trailing whitespace`, `new blank line at EOF`) are downgraded from blocking to **advisories**. The `git diff --check` phase now passes with the advisories exposed instead of failing, and the advisories are printed in text, JSON and log; they create no block of their own. Whitespace that indicates a real defect (`space before tab in indent`, `leftover conflict marker`) and any unrecognized reason keep failing closed, an exit code outside git's documented `{0,1,2}` set short-circuits the phase to `failed` with no advisories, and a blocking record is honored even at exit `0`. The change adds `Get-WhitespaceClassification`, `Get-WhitespaceDiffArguments`, `Invoke-GitWhitespacePhase`, `Test-PhaseMechanicalFailure` and the capture helpers, switches the two operative `git diff --check` phases to them, exposes `advisories`/`noiseLines`/`blocking` on those phases, renders advisories in `Write-TextSummary` (reading the field defensively, since `New-Phase` did not carry it at the time), and bumps `schemaVersion` to `gxmcp-pre-push/2`. `git` runs with a pinned `core.whitespace=blank-at-eol,blank-at-eof,space-before-tab` set and a `C` locale so the classified reasons and the batch of hygiene findings are stable; that pinned set does not close the class, since a per-path `gitattributes whitespace` attribute can still add or subtract one. Recorded debt: the new phase duplicates the body of `Invoke-NativePhase` because that function is intentionally left untouched. See the "Hygiene advisories" policy in `AGENTS.md`.

- Fork-local pre-push mechanical checker, phase shape: `New-Phase` now initializes `advisories`, `blocking` and `noiseLines` as empty arrays, so every phase has the same keys and consumers no longer need to special-case their absence; the defensive reads stay because tests build phases outside `New-Phase`.

### Fixed

- Fork-local pre-push mechanical checker, Rust lane state: an explicit `-CargoExecutable` that does not resolve to an existing file or command now reports `not-run`/`cargo-not-found` instead of three launch failures, and a missing `src/gx-engine` reports `not-run`/`engine-missing` instead of three launch failures. `notCovered` is seeded before the lanes and finalized after them, so an abort before the lanes still declares each advisory lane; an entry is removed when its lane runs and carries the lane note when it does not. Pinned by `test-pre-push-mechanical-checks.ps1`; mutation-checked by removing each guard and the final removal.

- Fork-local Engine backend wrapper, exit-code contract: `scripts/Invoke-GxMcpLocalBuild.ps1` reported exit `1` for every failed entry point instead of the child's code. With `$ErrorActionPreference = 'Stop'` the `Write-Error` in the failure branch was terminating, so the following `exit $LASTEXITCODE` never ran; a fake `build.ps1` exiting `7` produced `1`. The branch now captures `$LASTEXITCODE`, emits the same message non-terminating (`-ErrorAction Continue`) and exits with the captured code, matching the script header, the `LOCAL POLICY` block in `AGENTS.md` and the `Added` entry above. Verified on an isolated copy of both scripts: failure path `7` → `7` with `publish\config.json` byte-identical, success path `0` → `0` with `Engine.Backend` applied. Behavioral coverage now lives in `scripts/tests/test-fork-local-backend-helpers.ps1`.

- Fork-local pre-push mechanical checker, confidentiality: the JSON summary serialized each phase's `outputTail` with up to 60 raw lines, while `Protect-GxMcpReleaseText` was applied only to the log copy. All four capture points (native, whitespace, PowerShell parse and the new Rust lane) now redact the tail at capture, a raw copy is kept outside the summary so the release-phase "command not found" retag still matches, and the serialized JSON gets a final redaction pass so `reason`/`command`/snippets cannot leak either. Redaction is per line; a secret split across lines is a documented limit.

- Fork-local pre-push mechanical checker, contract guard: `Assert-ReleaseContractTopLevelSafe` now lives in the checker and runs before the contract dot-source, inside the top-level `try`, so an offending file is refused before it executes and the summary is still emitted. It rejects the `param`/`begin`/`process`/`dynamicparam`/`clean` blocks, any `using` statement, top-level statements other than functions, and bindings outside the two-name allowlist (plain `=`, literal RHS). It also fails when a contract function would shadow a checker function or a command the checker invokes (case-insensitive; the two intentional exports are exempt). Tests extract the guard through the same AST seam as the other production functions, keep the 25 table fixtures, and add file fixtures for `using`, function and command collisions, a positive control, a guard-before-dot-source offset assertion, and a sentinel that proves the offending contract did not execute. Mutation-checked by removing the production guard call. The guard is detection, not prevention: `using` is resolved at parse time, function bodies are not inspected, `#requires` is not parsed, there is no content hash, and `release-preflight.ps1`/`release-doctor.ps1` remain unguarded (upstream, reported). A new sanctioned upstream constant requires editing `Get-ReleaseContractAllowlist`.

- Fork-local pre-push mechanical checker, aggregate failure: when the release preflight exits non-zero with no failed phase (binary fingerprint binding, test-count), the prior output was `status=failed` with empty `failedPhases`. `details.aggregateFailure = { status, detail }` now carries the summary status and the last 20 redacted output lines; the phase lists stay faithful to real phases. The value is computed after the `unavailable` retag, so an unavailable phase never reports one; a missing/corrupt summary yields `status=$null`; the text summary prints the label and detail.

- Fork-local pre-push mechanical checker: the fork-local guard that required `scripts/release-contract.ps1` to declare **only** functions at top level no longer fails after the v4.0.0 sync, where upstream binds two named constants at top level (`$script:GxMcpReleaseWorkflowCheck`, `$script:GxMcpReleaseWorkflowAppId`). The guard now parses and validates the contract **before** the test dot-sources it, so an offending file is refused without first executing in the test scope; the tolerant shape is an explicit allowlist of those two names bound with a plain `=` to a literal constant, not any `script:`-scoped variable. Every other top-level statement is still refused - a pipeline, a call, a non-script scope, a compound assignment, a name outside the allowlist, a non-literal right side, a typed assignment, a `class`/`enum`, `exit`/`return`/`throw` - and the refusal names the line and a bounded snippet instead of only the AST type. The block pre-check now also rejects `dynamicparam` and `clean`, not only `param`/`begin`/`process`. Twenty-five synthetic `Parser.ParseInput` fixtures pin both directions, including a function with a non-empty body and a top-level pipeline, and a separate multi-statement fixture exercises the contract loop, so the acceptance branch no longer depends on the live upstream file. Mutation-checked: injecting `Get-Location | Out-Null`, injecting `$script:GxMcpMutationProbeOutsideAllowlist = 'x'`, emptying the allowlist, replacing the contract with `dynamicparam { }` and replacing it with `clean { }` each turn the guard red, and `release-contract.ps1` was restored byte-for-byte afterwards. Documented limits: `using` statements are resolved at parse time, so the refusal is detection rather than prevention; function bodies are not inspected; and the guard is a structural assertion over trusted upstream code, not a sandbox.

- Fork-local pre-push mechanical checker: `details.failedPhases` and `details.failedPhaseDetails` now report every phase the release preflight treats as failed, not only a phase whose status is exactly `failed`. `release-preflight.ps1` decides failure by negation - any per-phase status outside its allowed terminal set (`passed`/`skipped`/`unavailable`, plus `dry-run` under `-DryRun`) - so a timed-out phase (`timeout`, synthetic exit 124) and a phase still persisted as `running` (a preflight killed mid-run, which `release-doctor.ps1` already counts as a failure) are failures too. The checker had enumerated `failed` in positive, so those phases - the ones that explain a run that stopped short - were missing from the retained detail, contradicting the promise in `AGENTS.md`. It now mirrors the preflight's rule by negation, reading every field defensively: under `Set-StrictMode -Version Latest` a bare property read of a missing key throws, and the catch here would discard *every* `failedPhaseDetails` entry and report "unable to parse" instead - losing the evidence exactly in the scenario the change exists to make legible. All reads go through the shared `Get-GxMcpReleaseFieldValue`, envelope included, so a summary that parses but carries no `phases` yields an empty set instead of nothing, and a phase with no `status` is reported as a failure with its name intact. A `null` element of `phases` is filtered rather than reported as an all-null failed phase (`@($null).Count` is 1, so it would otherwise invent a phase), an entry with no usable name is labelled `(unnamed phase)` rather than emitted as a `$null` that would inflate the count, and `failedPhases` is projected from `failedPhaseDetails` so the two cannot disagree about which phases failed. `release-doctor.ps1` already carries the same envelope and null-element guards under issue #348, and the checker shares those. It deliberately diverges from the doctor on one point, though: the doctor classifies a failed phase by a positive list (`failed`/`timeout`/`running`) with a `Set-StrictMode`-free read, while the checker decides by negation, so an unlabelled or future status is a failure here and silently nothing there. The mirrored status set is pinned against the producer's literal declaration: rewrite that literal and this test turns red instead of the fork silently diverging. The pin reads the declaration, so a change to *how* the rule is applied rather than to its literal text (a later re-derivation of the same variable, say) is not covered. The retained set is the phases the producer recorded, which is not the same as the complete list of unfinished phases: a preflight killed mid-run leaves every phase of the in-flight parallel wave as `running`, and phases never started are absent from the summary altogether. A `running` phase in a completed run is impossible - both waves drive every phase to a terminal status before the preflight aggregates - so that mapping carries no false positive. Reverting the filter to `status -eq 'failed'`, or to a positive `failed`/`timeout` pair, turns the fork-owned regression red.
